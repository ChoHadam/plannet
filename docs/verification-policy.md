# 작업·검증 비용 관리

2026-10-04 · 사용자 요청에 따라 적용. 구현 모델은 Opus를 유지한다. 사용자별 서비스 데이터·인증·저장 보호를 유지하면서 중복 검증과 반복 문맥 읽기를 줄인다.

## 기본 루프

1. **범위 확인:** AGENTS와 배정 지시를 읽고, 관련 코드와 직전 보고의 필요한 부분만 확인한다. 전체 로드맵·전체 소스·과거 로그를 반복해서 읽지 않는다.
2. **검증 선택:** 바꿀 동작 → 실패 위험 → 해당 검사 파일/테스트 이름을 짧은 표로 정한다. 명시된 위험을 검사하는 기존 테스트를 우선 사용한다.
3. **구현·국소 확인:** 재현이 필요한 결함은 실패 재현 1회와 수정 후 검사로 확인한다. 실패 시 해당 사례부터 재실행한다. 의도적으로 정상 코드를 여러 번 망가뜨리는 mutation testing은 기본 절차에서 제외한다.
4. **완료 검사 1회:** 최종 소스에 타입 검사·영향 파일 lint·선택한 동작 검사를 수행한다. 이후 실행 코드와 테스트 조건이 같으면 같은 검사를 다시 실행하지 않는다. 문서 수정으로 앱 회귀를 다시 돌리지 않는다.
5. **총괄 검토:** 변경분·검증 요약·필요한 실패 부분을 확인한다. 총괄은 담당자가 통과시킨 명령을 습관적으로 다시 실행하지 않는다. 실제 결함·누락된 위험·검증 후 코드 변경이 있을 때만 추가 지시한다.

## 변경별 검사 선택

| 변경 | 기본 범위 | 확대 조건 |
|---|---|---|
| 문구·색상·간격 | 영향 파일 lint, 바뀐 화면의 필요한 폭·키보드 확인 | 구조·상태 동작이 달라진 경우 |
| UI 동작·모달·선택 | 타입 검사, 영향 파일 lint, 해당 흐름·모바일/키보드 검사 | 인증 경계·store/저장 경로를 수정한 경우 |
| 저장·인증·주차 계약 | 타입/API 검사와 해당 실패·경계·데이터 보존 사례 | 공유 프로토콜 영향이 있으면 관련 회귀 확대 |
| 의존성·배포 버전 | 고정 버전의 빌드와 핵심 통합 회귀 | 런타임 호환성·보안 경계 문제가 발견된 경우 |

전체 인증·저장·템플릿 묶음은 매 작업의 기본값이 아니다. 배포 후보 통합 검증 또는 여러 영역에 영향을 주는 변경에서 실행한다. 이미 시작한 저장 프로토콜 변경의 필요한 검사를 비용만을 이유로 생략하지 않는다.

## 실행·문맥 관리

- 같은 단계에서 여러 테스트 설정이 각각 production 빌드를 하는지 먼저 확인한다. 새 검사는 가능하면 관련 기존 스위트에 추가한다. 테스트 이름/파일 필터를 쓰고, 논리 검사에는 브라우저 서버를 띄우지 않는다.
- 기본 목표는 최종 소스의 필요한 빌드 1회다. 인증 모드·번들러·컴파일 입력이 다른 경우 추가 빌드가 필요할 수 있으며 이유를 기록한다. 빌드 재사용은 소스·의존성·빌드 옵션이 일치할 때만 허용한다. 실제 실행 서비스의 빌드는 사용하지 않는다.
- 출력은 파일에 저장하고 성공 시 종료 코드·통과 개수만 읽는다. 실패 시 관련 오류 주변만 읽는다. 긴 로그·전체 diff를 여러 번 출력하지 않는다.
- 긴 검사는 셸/프로세스가 기다리게 한다. LLM이 짧은 간격으로 로그를 반복 조회하지 않는다. 총괄 상태 확인은 `state.json`과 해당 단계 요약으로 시작한다.
- 단계별 새 Opus 세션을 유지한다. 진행 보고는 중요한 결과에만 짧게, 상세 보고 원본은 저장소 보고서 하나로 둔다. 기계용 결과는 경로·검사·상태만 담고 긴 문서 내용을 중복 복사하지 않는다.
- 필요 이상의 스크린샷 조합과 전 영역 테스트 추가를 피한다. 바뀐 레이아웃·동작에 필요한 표본을 고르되, 데이터 보존·계정 격리 위험을 누락하지 않는다.

검사 수나 토큰 절감률을 완료 목표로 삼지 않는다. 필요한 근거가 확보되면 끝내고, 재실행에는 변경·실패·미해결 위험 중 하나의 이유가 있어야 한다.
