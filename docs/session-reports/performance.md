## 무엇을 했나

같은 조건으로 먼저 측정하고, 가장 큰 두 병목만 좁게 고쳤다.

```
이전: 로그인 화면 ─┬─ 작업 공간·4개 편집기·사용법·이모지(가장 큼)·AI·dnd-kit·공휴일 ── 모두 첫 로딩
                   └─ AuthProvider → usePlannerSync → 모든 store
이후: 로그인 화면 ── 인증·랜딩만
      입장 후     ── 작업 공간(store·사이드바·헤더) ─┬─ 연 템플릿의 편집기만 (주소의 편집기는 DB 조회와 나란히)
                                                    └─ 사용법·이모지·AI는 처음 열 때
입력 1회마다: 전체 기록 정규화 비교 → 바뀐(새) 객체만 정규화 비교
```

| 영역 | 이전 | 이후 |
|---|---|---|
| 로그인 전 화면 | `page.tsx`가 작업 공간을 정적 import, AuthProvider가 store까지 끌어옴 | 작업 공간은 입장 뒤 로드. 동기화 인스턴스 보관을 store 없는 `lib/plannerSyncInstance.ts`로 분리(로그아웃 저장 대기는 같은 인스턴스) |
| 편집기·사용법 | 레지스트리가 4개 편집기·사용법을 정적 import | 템플릿별 지연 로드(`lib/lazyComponent.tsx`). 편집기 자리에는 `편집 화면을 불러오는 중...`(role=status) |
| 이모지·AI | 항상 포함, AI 패널은 처음부터 마운트 | 처음 열 때 로드. AI는 한 번 연 뒤 계속 마운트(대화 유지) |
| 입력마다 저장 비교 | 모든 플랜을 `canonicalJson`으로 두 번 직렬화 | 같은 참조는 같은 내용으로 보고 건너뜀. 최신화가 같은 내용을 받으면 기존 참조를 유지 |

**`next/dynamic`을 쓰지 않은 이유:** 처음엔 `next/dynamic`으로 바꿨다. 바이트는 줄었지만 주소로 연 편집기 표시가 110 → 850ms로 늦어졌다. React 19 Suspense의 표시 지연(경계마다 약 300ms)이 작업 공간 → 편집기로 두 번 이어졌기 때문이다. `lazyComponent`는 Suspense 없이 모듈 캐시와 effect로 불러오고, 로드 실패 시 자동 새로고침 없이 안내만 한다(미저장 수정 보호).

## 측정

M2 Max·32GB·macOS 14.5, Node v23.11.0, Chromium 145 headless 1440×1000. 같은 `start-web.mjs` 격리 production 빌드(webpack, `next start` gzip), 가상 계정·플랜, 모든 API는 브라우저 가로채기. 시나리오마다 새 컨텍스트 7회의 중앙값. **로컬 실험실 값이다. 실제 사용자 지표(LCP·INP·CLS)나 네트워크 지연이 있는 환경의 값이 아니다.**

| 시나리오 | JS 전송량 | 변화 | 스크립트 수 | 표시까지(중앙값) |
|---|---|---|---|---|
| 로그인 전 화면 (401) | 292.9 → 140.8KB | **−51.9%** | 10 → 7 | 96 → 69ms |
| 작업 공간 빈 화면 (`최근 작업`) | 292.9 → 188.6KB | **−35.6%** | 10 → 9 | 108 → 91ms |
| 주소로 연 Daily (20개 할 일) | 292.9 → 212.4KB | **−27.5%** | 10 → 11 | 110 → 138ms |
| 주소로 연 만다라트 | 292.9 → 195.0KB | **−33.4%** | 10 → 10 | 112 → 134ms |

주소로 연 편집기는 작업 공간 코드를 받은 뒤에 DB 조회가 시작되는 순서 한 단계가 늘어 로컬에서 약 25ms 늦다. 편집기 코드는 DB 조회와 나란히 받는다(`parsePlanSelection`으로 템플릿만 읽음, 선택은 기존대로 조회 뒤).

입력 1회의 `PlannerSync.capture()` (Node 단독 함수, Daily 플랜당 할 일 20개, 30회 중앙값/p95, 이전·이후 소스를 번갈아 2회 반복):

| 플랜 수 (JSON 크기) | 이전 | 이후 (앱 상태: 불러온 참조 공유) | 이후 (최악: 모든 참조가 다름) |
|---|---|---|---|
| 10 (15KB) | 0.98 / 1.20ms | **0.21 / 0.30ms** | 0.99~1.14ms (변화 없음) |
| 100 (150KB) | 8.6 / 8.9ms | **0.26 / 0.31ms** | 8.9~10.1ms (변화 없음) |
| 1000 (1.5MB) | 86 / 89ms | **0.69 / 0.91ms** | 86~100ms (변화 없음, 실행 간 차이 ±4%) |

이 값은 브라우저 INP가 아니다. 렌더링·store 구독 비용은 포함하지 않는다. 이전에는 탭 재표시마다 조건부 조회(304 포함)가 기준 기록을 새 객체로 바꿔 항상 최악 경우가 됐다. 이제 내용이 같으면 참조를 유지한다.

## 저장 보호 근거

`a === b`는 그 순간 같은 직렬화이므로 기존 비교와 결과가 같다. 불러온 DB 데이터는 원래부터 store에 같은 참조로 넘어갔고, store 동작은 모두 새 객체로 갱신한다(제자리 변경 없음 확인). 최신화의 참조 재사용은 정규화 비교가 같을 때만 한다. 임시 보관 시점·requestId 재전송·ACK 중 편집·계정 경계·저장 계약은 바꾸지 않았다.

## 한계·후속

- 실험실 값만 있다. 실제 네트워크에서는 입장 후 작업 공간 코드 요청이 순서상 한 단계 늘어난다. 실제 사용자 LCP·INP는 미측정
- **기존 동작 발견:** 이모지 그림을 라이브러리 기본값인 `cdn.jsdelivr.net`에서 받는다(외부 요청). 이번 범위 밖이며 CSP·개인정보 관점의 후속 검토 대상이다
- 최신화로 store가 교체되지 않은 종류는 서버 내용이 바뀐 경우 참조가 달라 최악 경우 비용으로 돌아간다(새로고침이나 다음 최신화에서 회복). 최신화·ACK 응답 크기와 렌더 쪽 전체 구독·정렬 비용 축소는 측정 뒤 별도 단계
- 남은 큰 묶음은 react-dom·Next 런타임(약 130KB 압축)으로 이번 범위에서 줄일 수 없다
