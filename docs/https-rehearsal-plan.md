# 최신 코드 HTTPS 배포 리허설 계획

2026-09-28 · 상태: **실행 완료** · [검증 결과](session-reports/https-rehearsal-current.md) · [로드맵](roadmap-status.md)

**결과:** 최종 HTTPS 24개·실제 PostgreSQL API 56개 통과(실패·건너뜀 0). V2→V3 가상 계정·플랜·영수증 메타데이터 보존과 원래 ACK 재전송을 확인했다. 첫 전체 실행의 테스트 대기 시간 실패 1건을 수정하고 단독·전체 재검증을 마쳤다. 전용 클러스터는 정상 상태로 유지했고 기존 로컬 서비스는 변경하지 않았다. 아래 표는 완료한 실행 범위와 기준이다.

**목표:** 미커밋 변경까지 포함한 현재 코드가 HTTPS Gateway·실제 Web/API 이미지·PostgreSQL 환경에서 로그인, 자동 저장, 복구를 정상 처리하는지 확인한다. 완료하면 홈서버 이전에 사용할 검증된 소스·이미지·결과를 확보한다.

```mermaid
flowchart LR
    A["환경·기존 검증 데이터 확인"] --> B["최신 검증 시나리오 보완"]
    B --> C["소스 고정·이미지 빌드"]
    C --> D["전용 HTTPS 환경 배포"]
    D --> E["정상·복구·장애 흐름 검증"]
    E --> F["결과·이미지 식별자 기록"]
```

## 실행 순서

| 단계 | 작업 | 통과 기준 |
|---|---|---|
| 1. 실행 환경 확인 | Docker·전용 kind 클러스터·검증 포트·자체 서명 인증서의 유효기간 확인. 기존 검증 DB/PVC와 자격 증명 파일의 짝 확인 | 전용 환경을 확실히 식별. 기존 클러스터 재사용 시 연결된 작업 폴더와 자격 증명 유지 |
| 2. 테스트 보완 | 기존 17개 시나리오를 최신 로그인 랜딩·계정 이메일·DB/임시 보관 정책과 대조하고 아래 추가 검증 구현 | 테스트 이름과 실제 수행 동작 일치. 가상 계정·가상 플랜만 사용 |
| 3. 배포 대상 고정 | 미커밋·새 파일을 포함한 소스 스냅샷 생성, 파일 해시 기록, 새 Web/API 이미지 빌드, 매니페스트 검사 | V3 migration과 최신 웹 변경 포함. 소스·이미지 ID 추적 가능, 비밀 파일 미포함 |
| 4. HTTPS 배포·DB 확인 | 기존 `verify-local.sh`를 바탕으로 전용 환경 배포. 인증·저장 활성화, 실제 Pod 이미지 ID·DB 역할·PVC·migration 확인 | HTTPS health 정상, 앱 DB 역할은 비관리자, migration 1·2·3 성공, 실패 이력 0 |
| 5. 결합·장애 검증 | 기존 17개와 추가 시나리오 실행. DB/API 중단·복구 시험은 같은 클러스터에서 순차 실행 | 계정 격리·데이터 보존·재시도·복구 성공. 실패 시 원인 수정 후 영향 범위 재검증 |
| 6. 결과 확정 | 테스트 결과·실패 추적·이미지 ID·소스 해시·DB 확인 결과 저장. 로드맵과 배포 준비 문서 갱신 | 최종 이미지와 최종 결과가 같은 소스 기준. 장애 시험으로 바꾼 서비스 상태 복구 |

## 최신 변경에 맞춰 추가할 검증

| 대상 | 핵심 시나리오 | 기대 결과 |
|---|---|---|
| 로그인 랜딩·계정 | 로그인 전 가상 브라우저 기록 보유, 인증/DB 확인 실패, 서로 다른 계정 로그인, 로그아웃 | 인증·DB 확인 전 기록 미노출, 이메일로 계정 구분, 로그아웃 후 플래너 접근 차단 |
| 자동 저장 임시 보관 | 650ms 대기 중 새로고침, 저장 응답 수신 전 새로고침, 저장 중 추가 수정 | 같은 계정의 변경분만 복구. 같은 요청 ID로 재시도해 버전은 한 번 증가하고 후속 수정도 보존 |
| 임시 보관의 경계 | 저장 완료, 다른 계정, 임시 저장 차단, 충돌 후 새로고침, 저장 실패 중 로그아웃 | 완료 후 임시 키 제거, 전체 본문 영구 캐시 없음, 다른 계정 초안 미적용. 임시 저장 차단에도 DB 저장 가능. 충돌 초안 보존·미저장 로그아웃 방지 |
| 조건부 조회 | HTTPS Gateway 경유 최초 200 → 같은 ETag로 304 → 수정/삭제 후 200. 계정 불일치 요청도 함께 검사 | ETag·`no-store` 전달, 304 본문 없음, 변경 후 최신 내용 반환. 인증/계정 검사를 생략하지 않음 |
| 축소된 저장 영수증 | 저장 후 다른 수정/삭제를 거쳐 과거 요청 재전송. 요청 ID를 다른 본문에 재사용 | 원래 성공 응답 복원, 중복 저장 없음, 다른 내용 재사용은 409. DB 영수증에 플랜 본문 없음 |
| V3 업그레이드 | 가상 데이터가 있는 V2→V3 경로와 최신 이미지의 기동 확인 | 계정·플랜 전체 내용/버전 및 영수증 ID·해시·메타데이터 보존. 재시도 결과 동일 |

기존 검증의 HTTP→HTTPS 전환, 쿠키 보안 속성, CSRF, AI 접근 제한·한도, 공용 백업 차단, 네트워크 접근 제한, DB/API 재시작 후 영속성도 유지했다. 계획 시점의 응답 유실 시나리오는 **재시도 성공 뒤** 새로고침했으므로, 이번에 응답을 받기 전 새로고침·같은 요청 ID 재전송·원래 ACK 비교로 강화했다.

V2 검증 데이터가 기존 전용 DB에 있다면 업그레이드 전에 보존 기준을 확보한다. 이미 V3이거나 새 DB라면 별도 일회용 V2 스키마의 Flyway 업그레이드 검증을 사용한다. DB 테스트는 실제 검증용 PostgreSQL 연결을 확인하고 실행·건너뜀 수를 구분한다. `RUN_API_TESTS=1`만으로 DB 테스트까지 실행됐다고 판단하지 않는다.

## 환경과 결과의 범위

- 실행 경로: `https://plannet.test:19643` → Envoy Gateway → 실제 Web/Spring 이미지 → 검증 전용 PostgreSQL/PVC. HTTP 검증 포트는 `19680`, 클러스터는 `plannet-verify`다.
- 자체 서명 인증서와 가상 Google·AI 제공자를 사용한다. 이 결과는 공인 인증서·실제 Google/AI·홈서버 검증과 구분한다.
- 현재 사용하는 `localhost:3000`, 로컬 DB `15432`, 실제 계정/플랜, DuckDNS·Google 운영 설정은 이번 검증 대상에 포함하지 않는다. 테스트가 주입한 장애는 검증 환경 안에서 복구한다.
- 산출물은 기존 전용 작업 폴더 아래 실행별로 보존한다. 소스/이미지 해시, 테스트 통과·실패·건너뜀 수, 실패 원인·수정 이력, V3 보존 검증, 핵심 화면을 기록한다. 기존 167개 검증 결과와 새 HTTPS 결과를 중복 합산하지 않는다.
- 최종 결과에 영향을 주는 소스를 수정하면 스냅샷·이미지를 다시 만들고 관련 검증을 갱신한다. 검증 종료 후 클러스터를 유지하는지 정리하는지도 기록한다. 정리는 이번 검증 자원에만 한정한다.
- 역할: 기존 요청대로 Opus에 테스트·검증 도구 보완을 맡기고, 총괄은 범위 확정·코드 검토·환경 실행·결과 인수를 담당한다. 공유 클러스터의 장애 시험은 병렬 실행하지 않는다.

**사용자 개입:** 정상 진행에는 추가 입력이 필요 없다. Docker 재시작처럼 현재 서비스에도 영향을 줄 수 있는 조치나 OS 권한이 필요해진 경우에만 구체적인 사유와 함께 요청한다. 이번 계획에는 커밋·푸시·공개 배포를 포함하지 않는다.
